# 桌面稍后读助手规划草案

状态：规划与官方资料调研，未实施。日期：2026-11-05。

## 1. 产品目标与首版边界

把现有命令行 PDF 服务演进为普通用户可以安装、打开、退出的桌面应用。扩展采集内容，应用离线保存、管理、阅读并按需导出。保存进内容库不要求先生成 PDF。

首版继续聚焦 ChatGPT 的所选消息；数据格式预留文章，暂不开发文章抓取。默认本地存储，不要求账号或联网登录。远程服务模式可作为兼容选项保留。

建议先支持 macOS，随后验证 Windows；Linux 排在后续阶段。这是建议的开发顺序，目标平台尚未由用户确定。

首版流程：

1. 安装客户端并完成一次扩展连接设置。
2. 在 ChatGPT 选择消息，选择“保存到客户端”“导出文件”或“保存并导出”。
3. 客户端未运行时由扩展唤起；客户端已运行时复用唯一实例。
4. 显示接收进度，完成离线资源写入后才确认保存成功。
5. 用户可以立即进入阅读，也可以继续浏览，稍后在客户端整理。

“导出文件”也可通过客户端执行，但不强制把临时导出永久收录到内容库。扩展仍可提供已有的远程服务模式。

## 2. 技术路线：优先验证轻量系统 WebView

| 路线 | 依赖与体积 | 原貌与 PDF | 建议 |
| --- | --- | --- | --- |
| Tauri 2 + Rust + 系统 WebView | 不自带完整浏览器；Windows 需要 WebView2 运行时，Linux 有 WebKitGTK 依赖 | 不同平台渲染内核不同，需原生 PDF 适配及回归 | 轻量目标下首选验证 |
| Electron + Node.js + 内置 Chromium | 应用自带浏览器内核，体积和更新负担较大 | 可用 webContents.printToPDF，更接近当前 Chromium 流程 | 原貌一致性优先时的备选 |
| 桌面壳 + 原 Python/Node/TeX/外部 Chrome 全套 | 最快包出可运行版本，但依赖仍多 | 基本沿用现有结果 | 仅可作为短期迁移方案，不作为最终轻量架构 |

Tauri 在 macOS 使用 WKWebView，在 Windows 使用 WebView2，在 Linux 使用 WebKitGTK；因此“不再调用外部 Chromium”可以实现，但 Windows 的 WebView2 本身仍采用 Chromium 技术。Electron 同样无需用户安装 Chrome，不过会把 Chromium 随应用分发。

依据：[Tauri 系统 WebView](https://v2.tauri.app/reference/webview-versions/)、[Electron PDF API](https://www.electronjs.org/docs/latest/api/web-contents#contentsprinttopdfoptions)。

### 系统 WebView 的 PDF 边界

- macOS：研究 WKWebView 的 createPDF 与 AppKit 打印操作两条路径。不能把“能生成 PDF”当作已支持 A4 多页、纸张边距、标题书签和正确分页。
- Windows：WebView2 提供 PrintToPdfAsync，仍需验证背景、字体、公式、分页和目录。
- Linux：后续单独验证打印管线及发行版依赖，不先承诺与 macOS/Windows 同等效果。
- 阅读目录、正文目录页、PDF 侧栏书签分别实现和验收。系统打印若不产生书签，需要结合实际页面位置后处理，不能仅复制 HTML 标题就宣称书签跳转正确。
- 当前 Chromium 专用分页脚本不能不经验证就用于 WebKit；提取通用规则，允许引擎有单独实现。

依据：[WKPDFConfiguration](https://developer.apple.com/documentation/webkit/wkpdfconfiguration)、[WKWebView 打印](https://developer.apple.com/documentation/webkit/wkwebview/printoperation(with:))、[WebView2 PDF 打印](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/print)。

### 决策门槛

先做独立技术验证，再确定正式客户端框架。以实际保存的“408 计组大题模板手册”为首批样本，验证：原貌阅读、代码全文、多页 PDF、彩色图整体换页、超高图缩放、中文字体、公式、搜索正文和 PDF 书签。记录冷启动、接收耗时、安装体积、空闲/阅读/导出峰值内存。

若系统 WebView 的核心样本无法在可接受的适配范围内通过，应明确选择 Electron，或提供可选渲染组件；不得静默降级成全页图片 PDF。选择需重新评估，不承诺尚未测量的体积和内存数字。

## 3. 扩展唤起与通信

推荐：Native Messaging 用于启动和握手，小型连接程序负责启动独立客户端进程，再通过本机 IPC 传递命令。客户端单实例，扩展连接断开不应杀掉客户端或使已接收任务丢失。

浏览器只能启动已安装并注册的 Native Messaging Host，不能随意执行用户电脑上的应用。安装器或客户端首次运行引导负责注册，普通用户不手动编辑配置。浏览器家族的注册位置、扩展 ID 及支持情况不同，提供连接诊断和修复入口，按 Chrome、Edge、Brave 等逐项验收，不以“Chromium 内核”代替兼容性测试。

大内容不放进唤起 URL，也不依赖单条 Native Messaging 消息。采用分块、校验和、提交确认和任务查询：

- 控制：协议版本、连接状态、启动、创建接收任务、查询任务、打开条目。
- 数据：分块上传归档包；可以经过 Native Messaging 分块转发，或握手后使用短期鉴权的回环端点。首个原型比较两者开销后确定。
- 完成：资源校验并原子提交后返回稳定条目 ID；客户端已收到但扩展没收到响应时，重试不得重复收录。
- 本机通信限定扩展来源与配对凭据；若有 HTTP，只监听回环地址，不开放局域网。网页快照没有管理应用的权限。

Chrome 文档规定 Native Host 向扩展单条消息最大 1 MB，扩展向 Host 最大 64 MiB；现有长会话载荷可能超过这个范围，必须设计分块协议。

依据：[Native Messaging 注册、启动与消息限制](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)。

备选：自定义协议（如 readerapp://）用于显式唤起和安装引导，配合现有本机 API 传输。协议只携带短期任务标识，首次可能出现浏览器或系统确认。它不等价于所有浏览器上无提示后台启动。

依据：[Tauri Deep Linking](https://v2.tauri.app/plugin/deep-linking/)。

退出行为：关闭窗口与退出应用清楚区分；用户完全退出后停止本地接收，扩展下次主动保存时再唤起。可选托盘后台接收，默认不开机自启。不把关闭浏览器与删除本地内容绑定。

## 4. 内容库与持久化

内容库以可独立备份的内容包为核心，SQLite 保存管理信息与搜索索引，资源按哈希去重。PDF 是派生产物，不能成为唯一正文。

建议的内容包包含：

- manifest：包版本、条目/修订 ID、来源类型、来源 URL、标题、捕获时间、原始视口宽度、主题、采集器版本、资源完整性及缺失警告。
- snapshot：去除脚本、已冻结样式的 HTML，附带本地字体、图片、SVG、画布图片等资源。
- semantic：按顺序保存的消息/段落/代码/公式/标题结构；ChatGPT 额外包含角色、消息 ID、模型及所选消息范围。
- headings：稳定标题 ID、级别、文本与跳转目标，作为阅读目录基础。
- text：用于搜索的正文；不能仅依赖 PDF 提取文字。
- generated：缩略图及可失效重建的 PDF 等派生文件。

保存三类内容的边界：原始采集记录保留用于诊断和未来重新处理；阅读快照经过清理，用于隔离显示；PDF 排版临时副本允许展开代码、整图换页和缩放。打印专用调整不反写用户阅读正文。

SQLite 管理条目、来源、修订、标签、收藏夹、阅读进度、标注、资源引用及任务状态。字体与大图片放文件系统，不把大型 Base64 HTML 长期塞进 SQLite。数据库提交和资源落盘按接收事务协调，启动时恢复未完成任务，清理无引用资源要经过引用核对及回收站保留。

同 URL 的重复收藏不覆盖已有内容：结合来源 ID、所选消息 ID 和内容哈希决定“完全重复”“同来源的新范围”“新增修订”。每次保存保留采集范围，避免选中两条回答后误把完整对话视为已归档。

中文搜索需验证分词或 n-gram 索引；不直接假定默认 SQLite 分词器能满足中文检索。搜索命中跳转与标注定位使用稳定块 ID 和文本上下文，避免只依靠 DOM 序号。

## 5. 客户端界面与阅读体验

首版采用内容导航、条目列表、阅读区三栏；阅读目录作为可收起侧栏或面板。窄窗口可切换为单列阅读。

- 导航：收件箱、未读、已读、星标、收藏夹、标签、回收站。
- 列表：标题、来源、保存时间、摘要、同步/接收警告；支持排序、筛选和批量操作。
- 阅读：默认网页原貌；缩放或适配宽度、全文搜索、标题目录、来源链接、阅读进度恢复。
- 代码：保留语法高亮；提供展开与复制。阅读时可以滚动，PDF 时自动展开。
- 图表：保留结构、颜色和标签；可放大查看，PDF 使用独立的整体分页规则。
- 整理：修改收藏标题、标记已读、收藏夹与标签、备注；正文高亮及锚点标注随后加入。

“原貌”并不等于修改整个正文 CSS 以强制随客户端主题变化。保留采集主题与快照宽度；另行提供适配宽度和将来的阅读模式，避免黑白主题切换破坏图表颜色与对比度。

归档内容在无应用权限的独立 WebView/隔离文档中显示，默认无脚本、不联网。应用自身的命令接口与归档正文隔离；不向正文暴露文件系统、进程或管理 API。依据：[Electron 不可信内容隔离原则](https://www.electronjs.org/docs/latest/tutorial/security)；Tauri 路线同样需要按能力和 WebView 边界落地。

## 6. 导出能力

| 格式 | 首版建议 | 转换来源与限制 |
| --- | --- | --- |
| PDF 原貌 | 必须 | 从打印副本生成，正文可搜索，公式/图片按实际能力处理；保留当前书签与目录页两个独立开关 |
| 离线 HTML | 必须 | 单文件或 HTML+资源包；实现可移植资源链接 |
| Markdown / TXT | 必须 | 从结构化正文转换，说明无法表达的图表会以图片或附件保留 |
| JSON / 完整归档包 | 必须 | JSON 提供语义与元信息；完整包包含资源，用于迁移与恢复 |
| 批量导出 | 首版基础版 | 文件名冲突、时间戳、任务队列、取消及部分失败反馈 |
| DOCX / EPUB | 后续 | 侧重重新排版和阅读，不承诺网页原貌 |

为轻量目标，不默认分发完整 TeX。现有 Pandoc/XeLaTeX 作为高级可选组件或远程服务能力，首版基础格式不依赖用户装 Python、Node、Pandoc、TeX 或外部 Chrome。

## 7. 现有工程的迁移

可复用：消息选择交互、当前分支与 DOM 捕获、资源冻结、HTML 清理、标题提取、文件名规则、分页回归样本、Markdown/公式转换规则。

需要改造：从“提交一个 PDF 任务”抽出“采集并提交归档内容包”；传输层独立；原貌阅读与 PDF 排版独立；将任务表升级为持久内容库。

不要长期同时捆绑 Python 服务、Node 服务和 Rust 服务。先通过接口兼容完成迁移，再逐步收敛核心实现；任何过渡 sidecar 都需要自带运行环境和明确移除目标，不能要求普通用户安装开发依赖。

建议未来开发目录独立为 desktop-client/，数据和协议说明也独立维护。旧 local-extension/ 按用户要求保持不动；当前 exporter-extension/ 后续增加客户端目标和传输适配。此草案不创建应用目录或修改现有行为。

服务适配器提供归档接收、任务进度与导出能力查询。使用版本化握手和能力协商，不假定新版扩展和旧客户端总是同步更新。

## 8. 分阶段交付与验收

### 阶段 0：技术验证与选型

- macOS 系统 WebView 加载真实离线快照并输出多页 PDF。
- 若 Windows 是首发目标，同时验证 WebView2，避免只凭 macOS 结果确定跨平台路线。
- Native Host 在冷启动、客户端已运行、异常退出后恢复三种状态下完成保存握手。
- 大内容分块、重复重试、离线资源、同来源不同选择范围均可保存。
- 验证长代码、公式、彩色长图整体换页、PDF 目录页与书签、字体搜索和复制。
- 实测安装体积、资源/内存与性能，再决定 Tauri 或 Electron。

### 阶段 1：可安装、可保存、可阅读

安装包与签名/公证、连接引导、按需唤起、单实例、离线内容库、原貌阅读、目录、搜索、标签/收藏夹、阅读状态、备份恢复，以及 PDF/HTML/Markdown/TXT/JSON 导出。

验收：用户不需要命令行；客户端退出后可以从扩展再次启动；断网能阅读；资源完整性有可见反馈；保存成功后异常退出不丢内容；支持卸载应用时明确选择是否保留个人资料。

### 阶段 2：整理与迁移

批量整理导出、内容修订、正文标注、阅读锚点、可选导出组件、数据迁移和自动更新。历史 PDF 可作为文件条目导入；若旧任务保留 HTML/正文则进一步转换，不能从 PDF 凭空恢复完整原貌源数据。

### 阶段 3：通用稍后读

在相同内容包协议上加入文章采集适配器、正文提取与阅读模式。之后再评估订阅、移动端、同步、OCR 和 AI 能力，首版不建立这些依赖。

## 9. 建议确认的产品决策

后续实现前需要确定：首发 macOS 还是 macOS+Windows；轻量程度与跨平台原貌一致性哪个优先；是否需要托盘常驻；是否保留远程服务器模式；是否首版包含正文高亮。

当前建议：Tauri 系统 WebView 优先验证、macOS 起步、本地优先、按需启动、原貌归档与基本整理先完成，文章采集与云同步后置。
